# STUNMESH Android application security audit

**Audit window:** 2026-09-13 01:01:47–11:01:47 UTC (ten hours; investigation ongoing).

**Audited tree/release:** `e0cc30951e24ec018423bb113acfe7849f9836d5` (tree `89fec5301ded70d7b76830653cea96d51c79f45d`), `v0.2.1`.
**Fork:** <https://github.com/snf/stunmesh-android>. This branch adds audit-only JVM tests and this report; no production code, phone, NAS or VPS service was changed. The companion Go/mobile-core report is in the sibling `stunmesh-go` checkout.

## Deployment decision and authentication answer

**Do not install the current STUNMESH APK to provide trusted entry into the home network.** The embedded Go core has a confirmed endpoint-record-to-WireGuard-UAPI injection that can turn possession of a configured peer's static private key into route takeover and plaintext traffic delivery to a newly enrolled peer, despite a configured WireGuard PSK. An arbitrary public DHT writer without the peer key could not do this in the control test. The source test uses the production Go mobile controller and wireguard-go with synthetic keys/in-memory TUNs in Linux; it has **not** yet been run on a real Android device. Separately, the Android VPN service does not implement the foreground lifecycle Android requires for reliable background/always-on operation (A-15).

The user's literal requirement that **WireGuard modules perform all peer authentication** is **not met**. Discovery records are authenticated by NaCl `box` in the Go core, using WG static key material outside the WG handshake and without the PSK. Android's app layer does not add a second peer identity mechanism, but it passes plugin and network configuration into that separate core authenticator. Ordinary tunnel packets use wireguard-go; the issue is that discovery can change wireguard-go's authorized configuration. See the Go report and `mobile/audit_security_test.go` for the detailed proof.

No deliberate backdoor or compromised Android runtime library was identified in the inspected Kotlin source, generated DEX comparison, or resolved runtime dependency scan. That is not a proof of absence: the official APK contains an upstream Go AAR, and the complete Android APK/AAR was not reproduced bit-for-bit or independently attested. The companion Go report separately documents byte-for-byte reproduction of two published Linux server binaries.

## Scope and trust boundaries

The Kotlin app owns Android's VpnService, tunnel editing/import/export, encrypted local configuration, underlay DNS callbacks, and the bridge into the Go AAR. The Go AAR owns STUN, OpenDHT/Cloudflare plugins, endpoint authentication, the UDP bind and wireguard-go. The Android manifest requests only `INTERNET` and `ACCESS_NETWORK_STATE`. In the merged release manifest, the exported launcher activity is user-facing; the exported VPN service requires Android's system `BIND_VPN_SERVICE` permission; AndroidX's profile-install receiver requires `android.permission.DUMP`. The debug build additionally exports the unprotected importer in A-11 (`security-audit-evidence/android-manifest-exposure.json`). No telemetry or analytics endpoint was identified in application source. This is a source/manifest observation, not an OS/network capture.

The OpenDHT HTTPS proxy is needed for periodic discovery records, **not** an ongoing tunnel-traffic hop. After punching, UDP WireGuard packets travel between the peers. The phone still uses STUN, the configured DHT proxy, and underlay DNS for refresh/recovery; if direct NAT traversal fails there is no relay fallback. STUN and DHT operators can observe the phone's source IP, probe/record timing, and public DHT indices; the endpoint record content is encrypted, and ordinary tunnel plaintext is not sent to them. Android's `VpnService.protect(fd)` is used for outer UDP and discovery HTTP/DNS sockets, so the tunnel does not route its own setup traffic into itself.

## Findings

### A-01 — High: authenticated discovery record can hijack Android WireGuard configuration

**Demonstrated in the linked Go mobile core; Android OS execution pending.** `mobile/controller.go:288–335` selects a decrypted endpoint string; `mobile/uapi.go:57–62` interpolates it into multiline wireguard-go UAPI. Embedded newlines can set `public_key`, `allowed_ip` and `preshared_key`. An audit-only end-to-end test proved new peer enrollment, PSK removal, route takeover, and plaintext packet delivery after a real WG handshake. It also proved rejection for a record encrypted by the wrong static key. The threat is a configured malicious peer or someone with that peer's static key, **not** any unauthenticated internet client. The PSK provides no defense for this control-plane step.

**Fix:** In the Go fork, parse/canonicalize the endpoint as a typed IP:port and reject all newline/control characters and invalid addresses before UAPI. Keep peer keys, PSKs and AllowedIPs immutable across discovery updates. Add the attack regression to CI and instrument a real Android VPN test before distribution. Android-side validation is useful defense in depth, but the Go core must enforce the invariant itself.

### A-02 — Medium: imported configuration can enable executable plugins despite the Android contract

`app/src/main/java/dev/stunmesh/android/config/TunnelYaml.kt:135–142` preserves an imported plugin `type`, and `TunnelConfig.kt:210` sends it unchanged through JSON. The Go mobile controller copies it to the shared manager, which accepts `exec` and `shell` and can start local processes. Android's `PluginDefinition` comment says only built-ins are valid, but that is not enforced. `SecurityAuditTest.importedYamlPreservesExecutablePluginTypeAcrossGoBoundary` passes, and the Go audit test demonstrates execution of a synthetic shell script in a Linux mobile-core build. Execution under Android OS app restrictions was **not verified**; it requires a user to import/select a malicious config and a runnable command path. No public DHT record can directly set the plugin type.

**Fix:** Reject non-`builtin` types at YAML import, editor save, JSON decode and Go mobile-core admission. Allowlist the built-in names required for the deployment (OpenDHT only if chosen). Remove `exec`/`shell` from a minimal mobile AAR if feasible.

### A-03 — High release-trust issue: source-built release still consumes upstream Go AAR

`settings.gradle.kts:28–33` fetches the Go core from `tjjh89017/stunmesh-go` GitHub release assets. `app/build.gradle.kts:25,140,153` makes **release** variants use that AAR even when a local AAR exists; there is no Gradle dependency-verification hash/lock for the asset. Thus compiling the forked Kotlin source is not enough to ship a self-audited binary. An upstream release asset/account change or compromised AAR remains in the phone trust chain. This is a supply-chain exposure, not evidence the current AAR is malicious.

**Fix:** Build the Go AAR from a reviewed, pinned fork commit with pinned Go/gomobile/NDK/modules, store/verify its SHA-256, make the release build consume **that exact local artifact**, and fail if it is absent. Pin Gradle dependency checksums using [Gradle dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html). A scratch-only release variant using the independently rebuilt AAR passed `testDebugUnitTest assembleRelease`; no production Gradle file was modified.

### A-04 — Medium availability risk: a missing Go core can still show a running VPN

`app/src/main/java/dev/stunmesh/android/tunnel/TunnelManager.kt:34–44` falls back to `StubBackend` when the Go class is absent or construction fails. `StubBackend.kt:25–46` establishes a real Android TUN and reports `UP` but forwards **no packets**. If `stunmeshCoreVersion` is omitted or the Go binding fails in a custom release build, the interface can look connected while selected traffic blackholes. The official APK did contain Go native libraries; this is a custom-build/release failure mode, not a claim that the official release is currently stubbed.

**Fix:** Prohibit the stub in release, fail the build without the exact AAR, and fail visibly at runtime if the core cannot load. Put a real handshake/packet health indicator on the status screen; `UP` alone means only device setup succeeded.

### A-05 — Medium: restored/corrupt encrypted config can be silently replaced

`ConfigRepository.kt:23–42` catches any read/decrypt/parse error and returns an empty `TunnelStore`. The next `save` (including a new active-tunnel selection) may replace a valid but temporarily unreadable config. `AndroidManifest.xml:9–12` allows backups, and the backup XML templates do not exclude `tunnel_config.bin`. A restored encrypted blob may lack its original Android Keystore key, then load as empty. This is an availability/data-loss scenario, not a demonstrated decryption break. `ConfigRepository.kt:15–16` also claims the key never leaves secure hardware; the code does not request StrongBox or inspect `KeyInfo.getSecurityLevel()`, so the hardware claim is unsupported. Android documents that [Keystore hardware backing depends on the device and key](https://developer.android.com/privacy-and-security/keystore) and that [backup rules govern files restored on another device](https://developer.android.com/identity/data/autobackup).

**Fix:** Distinguish missing file from decrypt/parse failure; surface and preserve the latter, with no overwrite until the user explicitly resolves it. Exclude the encrypted blob from Auto Backup unless a working portable-key restore design is added. Query hardware security level if making a hardware-backed claim. Keep user-selected plaintext YAML exports clearly labeled as secrets.

### A-06 — Medium on manual log export: redaction misses generic plugin credentials

`TunnelConfig.kt:53–69` redacts WG private/PSK fields and plugin keys matching `token|secret|password|passphrase`, but does not match `api_key` and only redacts string values. `StatusScreen.kt:124–142` includes the redacted config in a manually exported log. `SecurityAuditTest.genericApiKeyIsNotRedactedFromLogExportConfig` demonstrates an `AUDIT-CANARY` credential surviving that export. Current built-in Cloudflare's `token` key *is* redacted; a generic/future imported plugin credential is the precondition. The app's full tunnel YAML export intentionally contains secrets and should not be confused with the log export.

**Fix:** Export an explicit allowlist of diagnostic fields or redact all plugin-config values by default, preserving only known non-secret keys. Test `api_key`, nested/list values and custom plugin fields.

### A-07 — Low/medium local denial of service: unbounded imported document

`MainActivity.kt:102–105` uses `InputStream.readBytes()` on a user-selected content URI before YAML or wg-quick parsing, with no size limit. An untrusted provider or selected oversized file can exhaust process memory. This requires the user's import action and does not grant network access. SnakeYAML 2.5's default loader rejected a synthetic arbitrary Java object tag and a 100-entry collection-alias expansion in `SecurityAuditTest`; no YAML deserialization RCE was demonstrated. These checks do not bound the preceding file read or prove every YAML resource limit.

**Fix:** Bound reads to a small configuration limit, reject oversized/malformed inputs before persisting, and validate peer/plugin counts and string lengths.

### A-08 — Build and update-chain residual risks

The official `v0.2.1` APK SHA-256 is `9125271e7f205a3c222ada3704db86e9559fb359ca106c8305b4cece8aba97b3`. Android APK v3 signature verification passed; signer certificate SHA-256 is `6a732efac9b43afe280d513ca31b32c802537644b11333d5b34dd9d6179742cc`. I also downloaded and verified `v0.1.0-rc1`, `v0.1.0`, and `v0.2.0`: their local SHA-256 hashes matched GitHub's release asset digests and all four selected releases used that **same signing certificate** (`security-audit-evidence/android-release-signing-continuity.json`). This establishes signing-key continuity from the first selected prerelease, but the self-asserted certificate and GitHub metadata do **not** independently establish publisher identity on first install or prove every intervening release safe. There was no SourceStamp on `v0.2.1`. For your own Obtainium feed, use a stable self-controlled signing key, independently pin its certificate fingerprint, use monotonically increasing version codes, pin release commit/artifact hashes, and protect the release workflow; the fork's signing identity cannot upgrade an upstream-signed installed app in place.

The official APK and a source-built, unsigned `v0.2.1` APK using the **same upstream AAR** have identical entry names, manifest, both DEX files and 141/146 ZIP members. Four native library ZIP entries differ in packaging/non-runtime section metadata but have matching mapped segments when the ELF section-table pointer is normalized. This strongly supports Kotlin/manifest correspondence. The companion Go report also documents an **independent native rebuild**: after matching the upstream CI source/tool paths and `gomobile` temporary directory in an isolated audit build, the official and rebuilt ARM64/x86_64 ELF libraries differ only in build-ID notes; every other section, including executable code, is byte-identical. The 32-bit x86 executable section is byte-identical. ARMv7 has the same Go function layout and read-only data; every changed 32-bit `.text` word differs by the exact offset predicted by shifted `.text` and aligned target sections after an extra build-ID note (see `security-audit-evidence/go-aar-armv7-layout-normalization.json` in the companion Go fork). That is strong correspondence, not formal semantic proof. The archive, generated Java JAR and complete 32-bit native libraries are still not bit-for-bit reproduced. This materially reduces release-only backdoor concern, strongest for 64-bit phones, without making the vulnerable source safe.

The Gradle wrapper JAR matches the official Gradle 9.1.0 wrapper hash while the distribution URL/checksum pins Gradle 9.5.0. This is a reproducibility hygiene mismatch, not evidence of tampering; regenerate/verify the wrapper from the intended version. There is no dependency-verification metadata or lockfile. `settings.gradle.kts` also loads the [Gradle Foojay toolchain resolver](https://github.com/gradle/foojay-toolchains), which can resolve/download a JDK during a build; it is unnecessary if a reviewed JDK 21 is supplied explicitly. The exact resolved **runtime** Maven graph had 106 coordinates and no OSV-reported advisories as of 2026-09-13. All 73 cached content-bearing runtime AAR/JAR artifacts outside the separately audited Go AAR matched published SHA-256 metadata or independently downloaded bytes from Google Maven/Maven Central (`security-audit-evidence/android-runtime-artifact-published-sha256.json`). The **build-tool** graph had 115 coordinates; all 111 cached content-bearing build-tool JARs likewise matched their official repository bytes/checksums (`security-audit-evidence/android-build-tool-artifact-published-sha256.json`). This checks consistency with the publishers at audit time, **not** whether a publisher or its upload account was compromised. Seven OSV/GHSA entries appeared across six build-tool components: `commons-lang3 3.16.0` (GHSA-j288-q9x7-2f5v), `jose4j 0.9.5` (GHSA-3677-xxcr-wjqv), `bcpkix-jdk18on 1.79` (GHSA-wg6q-6289-32hp), `bcprov-jdk18on 1.79` (GHSA-574f-3g2m-x479 and GHSA-c3fc-8qff-9hwx), `jdom2 2.0.6` (GHSA-2363-cqg2-863c), and `kotlin-gradle-plugin 2.2.10` (GHSA-r937-wjx7-w2jp). They are **not in the app runtime graph**, and the scan does not establish exploitability in this build. Update and review build tools, particularly build-cache handling, before signing a release.

Of the 106 resolved runtime Maven coordinates, 92 are `androidx.*`, 12 are `org.*` (JetBrains/Kotlin, `org.yaml:snakeyaml`, JSpecify), one is `com.google.guava:listenablefuture`, and one is the Go AAR coordinate. This is a **resolved graph, not 106 independent binaries shipped in the APK**: some entries are BOM constraints or metadata. The direct UI dependencies are AndroidX Activity/Compose/Material/Core/Lifecycle; SnakeYAML parses imported configuration; the Go AAR supplies tunneling. The official APK has two DEX files and two distinct native libraries across four ABIs: `libgojni.so` and AndroidX's `libandroidx.graphics.path.so`. No analytics, ad, crash-reporting or general HTTP client SDK was declared by the app. AndroidX/Compose is the largest dependency family and a broader trust surface than a plain native UI; removing it would be a UI redesign, not a small audit hardening step. The Maven scan checks published advisories, not hidden malicious behavior, compromised build accounts or all transitive source code.

The Android `lintDebug` and `lintRelease` tasks passed; release lint produced 22 findings about versions, unused resources and UI style, no security-specific issue. Lint does not inspect the Go core or establish source provenance.

The inherited CI and release workflows also use version tags rather than immutable action commits. This Android repository itself inherits the same privileged `.github/workflows/cla.yml` pattern as the Go repository: `pull_request_target`/`issue_comment`, `tjjh89017/stunmesh-cla@main`, write permissions, and an optional PAT secret. GitHub Actions were disabled on both new `Owner` audit forks on 2026-09-13, and the API readback confirmed this. Remove or tightly pin and review the CLA workflow before re-enabling Actions, and protect any signed-release keys.

### A-09 — External DNS fallback is an explicit trust/metadata choice

`mobile/node.go:22` falls back to Google/Cloudflare public DNS addresses when Android has not supplied underlay resolvers. `StunmeshVpnService.kt:161–216` tries to feed underlay DNS via network callbacks, but there is an initial window and failure path. This is not a backdoor; it is a public DNS dependency and possible hostname metadata disclosure. For a private deployment, require known underlay DNS or document the fallback and prefer literal STUN/proxy addresses where operationally viable. HTTPS still protects DHT content in transit; DNS reveals queried hostnames.

### A-10 — Medium availability: Android's default refresh equals OpenDHT's expiry

`mobile/config.go:112–114` defaults to 600 seconds, while OpenDHT's [default stored-value expiration is ten minutes](https://github.com/savoirfairelinux/opendht/blob/master/include/opendht/value.h). One delayed or failed publish can leave the phone's record absent before the next cycle. Set a much shorter cadence (for example, one minute), leave OpenDHT dedup disabled, and verify reconnect after deliberately failed refresh cycles. This does not affect WG cryptographic authentication.

### A-11 — Medium for debug APKs: an exported receiver imports tunnel configuration from any app

`app/src/debug/AndroidManifest.xml:12–14` exports `ConfigImportReceiver` without a permission. The merged **debug** manifest contains it; the merged **release** manifest and official release APK do not (`security-audit-evidence/android-manifest-exposure.json`). `ConfigImportReceiver.kt:17–32` accepts base64 JSON from a broadcast, replaces a same-named tunnel and sets it active in the encrypted repository. Per [Android's receiver guidance](https://developer.android.com/privacy-and-security/risks/insecure-broadcast-receiver), an unprotected exported receiver can be invoked by other installed apps. A malicious local app could therefore change the configuration of an installed debug APK without the VPN user's import action; the changed tunnel may be used on a later start/restart. This is a source/merged-manifest finding, **not** a device exploit test, and it does not apply to the current release APK. The receiver does not itself read out existing secrets or start the VPN.

**Fix:** Do not use debug APKs with real tunnel credentials. Remove this broadcast hook or restrict it to a signature-protected test build and verify that no release variant exports it. Keep test injection behind explicit developer/test tooling, with a bound on the input size.

### A-12 — Conditional network reachability: a DHT proxy can redirect phone requests

The Go core's OpenDHT HTTP client follows redirects by default. The companion Go audit test proved that a configured synthetic **HTTPS** proxy could redirect its request to an unrelated local **HTTP** URL. On Android, these discovery sockets are protected out of the VPN, so a compromised configured proxy could cause requests to LAN destinations reachable from the phone's underlay. The test ran in an isolated Linux namespace, **not** on a phone or home router; no secret extraction or WG authentication bypass was demonstrated. Disable DHT redirects or restrict them to same-origin HTTPS in the Go core, and use an HTTPS proxy endpoint. Android documents that its [cleartext-traffic flag is best-effort for socket-level clients](https://developer.android.com/guide/topics/manifest/application-element), so it is not a sufficient fix by itself.

### A-13 — Medium user-action risk: full tunnel export has no in-app secret warning

`MainActivity.kt:81–90` writes `TunnelYaml.encode(tunnel)` to the user-selected document provider, including the WG private key, optional PSK and plugin API token. `TunnelListScreen.kt:150–152` exposes the action as an icon-only Export control, with no in-app warning that the destination receives plaintext credentials. The user must choose Export and a destination; this is **not** automatic exfiltration or a hidden backdoor. Show a clear warning before export, distinguish encrypted backup from plaintext configuration transfer, and label the file/output as sensitive.

### A-14 — Medium on manual log export: malformed imports can copy secret text into logs

`MainActivity.kt:96–121` appends a failed import's full exception message to the rolling log, which `StatusScreen.kt:124–142` includes verbatim in a user-selected log export. `TunnelYaml.decode` embeds SnakeYAML's parser message, and `WgQuickConf.decode` includes the full malformed line when `=` is absent. Two synthetic JVM audit tests show a credential-like canary from an invalid `private_key`/`PrivateKey` line appearing in those messages. Thus the A-06 config redaction does not ensure the whole log export is free of secrets. This requires a malformed user-selected import followed by manual log export; no automatic network exfiltration was shown.

**Fix:** Log a bounded error category and line number, without source lines, parser snippets, or raw exception messages. Treat the entire rolling log as sensitive until it is generated exclusively from allowlisted fields; test malformed private-key and plugin-token inputs.

### A-15 — High availability: VPN service never enters the foreground

`StunmeshVpnService.kt` starts the tunnel from `onStartCommand` but never calls `startForeground`; the manifest declares neither `FOREGROUND_SERVICE` nor a foreground-service type. The app targets API 36 and supports API 28+. [Android's VpnService documentation](https://developer.android.com/reference/android/net/VpnService) says that on Android 8.0+ the system gives a background-started VPN a short temporary allowlist and **will shut down the app unless it promotes the service to the foreground**. This is especially relevant when Android restarts an always-on VPN after reboot or process death. I did not run an Android device to measure when shutdown occurs, but the required call and manifest declarations are absent from the reviewed source and merged release manifest.

**Fix:** Add a persistent VPN status notification, foreground promotion during startup, and orderly demotion on stop. For target API 36, declare the appropriate foreground-service permissions and type; [Android documents `systemExempted` for VPN apps configured in system VPN settings](https://developer.android.com/develop/background-work/services/fgs/service-types). Verify actual eligibility and startup on the intended phone, including user-started, always-on reboot, app upgrade and network handover paths. If always-on is unsupported, explicitly opt out in the manifest instead of advertising it by default.

### A-16 — High release-key exposure risk: tag name executes as shell code in signing workflow

**Demonstrated locally without a GitHub run.** `.github/workflows/release.yml:31,69,79` interpolates `${{ github.ref_name }}` directly into `run:` shell scripts on a pushed `v*` tag. The synthetic tag `v$(printf${IFS}AUDIT_CANARY)` passes `git check-ref-format` and, when substituted into the actual line 31 command, causes Bash command substitution even though the value appears inside double quotes. The local result was `VERSION_NAME=vAUDIT_CANARY` (`security-audit-evidence/android-release-tag-injection.json`). [GitHub documents that context expressions are expanded into the temporary shell script before execution and that ref names are untrusted input](https://docs.github.com/en/actions/concepts/security/script-injections). No tag was pushed to GitHub, so this does not establish that GitHub accepts this specific name or that a remote secret was read. The precondition is control over a tag that triggers the release workflow; tag protection may restrict that control. The release job also decodes its signing keystore into `RUNNER_TEMP` and later runs a step with a write-capable `GITHUB_TOKEN`, so an injected command in that job could read the keystore or alter published artifacts. This is an independently important release-pipeline flaw even if the checked source APK is benign.

**Fix:** Treat the tag as data by passing it through a step `env:` variable and referencing the variable with a quoted shell expansion; validate it against a narrow release-tag pattern before use. Protect release tags, keep signing keys outside untrusted build contexts, and pin/review actions and the CLA workflow before enabling Actions on the fork. A local source build remains safe from this specific GitHub runner path.

## Verification and limits

With the Google Android SDK installed **only in the isolated audit workspace as authorized**, a full offline run of `testDebugUnitTest assembleRelease lintDebug lintRelease` passed: 19 JVM tests (15 baseline, four audit), zero failures (`security-audit-evidence/android-full-offline-verification.txt`). A later offline unit rerun passed 21 JVM tests, including the two additional malformed-import canary tests (`security-audit-evidence/android-import-error-secret-leak.txt`). The Go mobile core passed race-enabled tests and the synthetic end-to-end attack test. The official APK was signature/manifest/DEX-compared to a version-matched build; exact runtime/build-tool dependency coordinates were queried against OSV. A locally rebuilt Go AAR was produced and a scratch-only release build using that AAR passed.

A redacted history pattern scan inspected 149 blobs across 55 commits for common PEM private keys, AWS/GitHub/Stripe/Slack token formats and HTTP URL userinfo, finding zero matches (`security-audit-evidence/android-secret-pattern-scan.json`). It does not detect every secret shape or malicious change.

No Android emulator or device with KVM was available, so VPN lifecycle, Binder/Keystore behavior, network handover and actual cellular NAT traversal were **not** run on Android. The Google SDK, Gradle, AndroidX, Go runtime and all transitive source code were not independently audited. No compromised dependency or real-world exploitation was established, and no tool can prove absence of backdoors from a finite review.

**Release gate:** fix A-01 in the Go core; enforce built-in-only plugins; make release use a verified fork-built AAR and never silently stub; fix A-16 before enabling signed release workflows; implement the foreground VPN lifecycle; protect encrypted config against silent loss/backup restore; fix log redaction and import bounds; set a safe OpenDHT refresh cadence; review build-tool advisories; then install a self-signed fork APK on a test Android phone and verify handshake, traffic, disconnect, reboot/always-on restart, handover and update behavior before allowing access to the home network.
