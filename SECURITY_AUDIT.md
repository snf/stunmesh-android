# STUNMESH Android application security audit

**Audit window:** 2026-09-13 01:01:47–11:01:47 UTC (ten hours; investigation ongoing).

**Audited tree/release:** `e0cc30951e24ec018423bb113acfe7849f9836d5` (tree `89fec5301ded70d7b76830653cea96d51c79f45d`), `v0.2.1`.
**Fork:** <https://github.com/snf/stunmesh-android>. The audit branch and this root report are committed locally pending a disclosure decision; the public fork’s `main` remains at the audited upstream commit. This branch adds audit-only JVM tests and this report; no production code, phone, NAS or VPS service was changed. The companion Go/mobile-core report is in the sibling `stunmesh-go` checkout.

## Deployment decision and authentication answer

**Do not install the current STUNMESH APK to provide trusted entry into the home network.** The embedded Go core has a confirmed endpoint-record-to-WireGuard-UAPI injection that can turn possession of **either** the configured peer's or the phone's static private key into route takeover and plaintext traffic delivery to a newly enrolled peer, despite a configured WireGuard PSK. An arbitrary public DHT writer holding neither static key could not do this with valid generated keys in the control test; a malformed low-order configured key removes even that barrier (A-17). A malicious imported profile can also hide an unlisted peer in its endpoint field while leaving a valid TUN route. The source tests use the production Go mobile controller and wireguard-go with synthetic keys/in-memory TUNs in Linux; they have **not** yet been run on a real Android device. Separately, the Android VPN service does not implement the foreground lifecycle Android requires for reliable background/always-on operation (A-15).

The stated requirement that **WireGuard modules perform all peer authentication** is **not met**. Discovery records are authenticated by NaCl `box` in the Go core, using WG static key material outside the WG handshake and without the PSK. A public DHT writer who knows the two peer public keys can also reflect an existing ciphertext into the reverse record slot; it decrypts there because the record binds neither sender nor slot. With valid generated keys, that causes endpoint confusion/availability loss, not arbitrary ciphertext forgery; A-17 describes the malformed-key exception. Android's app layer does not add a second peer identity mechanism, but it passes plugin and network configuration into that separate core authenticator. Ordinary tunnel packets use wireguard-go; the serious issue is that discovery can change wireguard-go's authorized configuration. A literal WireGuard-only design must stop using the phone's static WG key as a discovery authenticator and constrain untrusted rendezvous data to a typed endpoint hint; the embedded WireGuard module still needs the key for its handshake. See the Go report and `mobile/audit_security_test.go` for the detailed proof.

No deliberate backdoor or compromised Android runtime library was identified in the inspected Kotlin source, generated DEX comparison, or resolved runtime dependency scan. That is not a proof of absence: the official APK contains an upstream Go AAR, and the complete Android APK/AAR was not reproduced bit-for-bit or independently attested. The companion Go report separately documents byte-for-byte reproduction of all 16 published server executable payloads and the mobile Java source JAR.

## Scope and trust boundaries

The Kotlin app owns Android's VpnService, tunnel editing/import/export, encrypted local configuration, underlay DNS callbacks, and the bridge into the Go AAR. The Go AAR owns STUN, OpenDHT/Cloudflare plugins, endpoint authentication, the UDP bind and wireguard-go. The app source manifest requests only `INTERNET` and `ACCESS_NETWORK_STATE`; the merged release APK additionally declares/uses an AndroidX app-scoped signature permission for dynamic receivers, with no extra platform data permission. The checked `v0.2.1` release APK is not marked debuggable. In the merged release manifest, the exported launcher activity is user-facing; the exported VPN service requires Android's system `BIND_VPN_SERVICE` permission; AndroidX's profile-install receiver requires `android.permission.DUMP`. The debug build additionally exports the unprotected importer in A-11 ([android-manifest-exposure.json](security-audit-evidence/android-manifest-exposure.json)). No telemetry or analytics endpoint was identified in application source. This is a source/manifest observation, not an OS/network capture.

The OpenDHT HTTPS proxy is needed for periodic discovery records, **not** an ongoing tunnel-traffic hop. After punching, UDP WireGuard packets travel between the peers. The phone still uses STUN, the configured DHT proxy, and underlay DNS for refresh/recovery; if direct NAT traversal fails there is no relay fallback. STUN and DHT operators can observe the phone's source IP, probe/record timing, and public DHT indices; the endpoint record content is encrypted, and ordinary tunnel plaintext is not sent to them. Android's `VpnService.protect(fd)` is used for outer UDP and discovery HTTP/DNS sockets, so the tunnel does not route its own setup traffic into itself.

## Findings

### A-01 — High: discovery and imported strings can hijack Android WireGuard configuration

**Demonstrated in the linked Go mobile core; Android OS execution pending.** `mobile/controller.go:288–335` selects a decrypted endpoint string; `mobile/uapi.go:57–62` interpolates it into multiline wireguard-go UAPI. Embedded newlines can set `public_key`, `allowed_ip` and `preshared_key`. An audit-only end-to-end test proved new peer enrollment, PSK removal, route takeover, and plaintext packet delivery after a real WG handshake. It also proved rejection for a record encrypted by the wrong static key when the configured key was valid. The usual threat is a configured malicious peer or someone holding either participant's static private key. Race-enabled synthetic tests demonstrated the attack with the peer key and independently with the phone key; an unrelated-key control failed ([mobile-either-static-key-forgery.txt](../stunmesh-go/security-audit-evidence/mobile-either-static-key-forgery.txt)). Another synthetic test proved that a rejected UAPI update can still leave its earlier injected peer and route installed; error handling after `IpcSet` does not roll back the change ([mobile-rejected-uapi-persists-peer.txt](../stunmesh-go/security-audit-evidence/mobile-rejected-uapi-persists-peer.txt)). A third test applied a subsequent well-formed endpoint update; the injected peer and stolen route still remained ([mobile-clean-refresh-persists-rogue.txt](../stunmesh-go/security-audit-evidence/mobile-clean-refresh-persists-rogue.txt)). Thus periodic discovery refresh does not repair an already changed WireGuard peer set. A-17 describes a malformed-key exception allowing an arbitrary DHT writer. The PSK provides no defense for this control-plane step.

**A second, local import path is demonstrated.** `TunnelYaml.decode` and `TunnelConfig.toJson` preserve hidden newlines in YAML `endpoint` and `allowed_ips` fields (`SecurityAuditTest.importedYamlPreservesHiddenUapiPeerInEndpointWithValidRoute`, `importedYamlPreservesHiddenUapiLinesInAllowedIpAcrossGoBoundary`; [android-hidden-endpoint-import.txt](security-audit-evidence/android-hidden-endpoint-import.txt), `android-hidden-allowed-ip-import.txt`). The Go core writes both strings into its **initial** UAPI. In the stronger endpoint variant, the profile's separate AllowedIPs remains a valid CIDR for Android's TUN builder, while a race-enabled synthetic wireguard-go test assigned that route to an unlisted peer without the listed peer's PSK ([mobile-imported-endpoint-hidden-route.txt](../stunmesh-go/security-audit-evidence/mobile-imported-endpoint-hidden-route.txt)). The AllowedIPs-only variant also installed a hidden peer and route inside wireguard-go, but Android may reject that malformed CIDR when creating the TUN; actual phone traffic effect of that latter variant remains untested. Both require a user to import/select a malicious profile or another local configuration compromise; a DHT writer cannot set these fields directly.

**Fix:** In the Go fork, parse/canonicalize discovered endpoints as typed IP:port and imported endpoints/AllowedIPs as typed IP:port/CIDRs; reject controls before any UAPI write. Keep peer keys, PSKs and AllowedIPs immutable across discovery updates. If any running WireGuard peer state is already altered, stop the VPN and rebuild the entire trusted peer set; a later clean refresh is insufficient. Add these attack regressions to CI and instrument a real Android VPN test before distribution. Android-side validation is useful defense in depth, but the Go core must enforce the invariant itself.

### A-02 — Medium: imported configuration can enable executable plugins despite the Android contract

`app/src/main/java/dev/stunmesh/android/config/TunnelYaml.kt:135–142` preserves an imported plugin `type`, and `TunnelConfig.kt:210` sends it unchanged through JSON. The Go mobile controller copies it to the shared manager, which accepts `exec` and `shell` and can start local processes. Android's `PluginDefinition` comment says only built-ins are valid, but that is not enforced. `SecurityAuditTest.importedYamlPreservesExecutablePluginTypeAcrossGoBoundary` passes, and the Go audit test demonstrates execution of a synthetic shell script in a Linux mobile-core build. Execution under Android OS app restrictions was **not verified**; it requires a user to import/select a malicious config and a runnable command path. No public DHT record can directly set the plugin type.

**Fix:** Reject non-`builtin` types at YAML import, editor save, JSON decode and Go mobile-core admission. Allowlist the built-in names required for the deployment (OpenDHT only if chosen). Remove `exec`/`shell` from a minimal mobile AAR if feasible.

### A-03 — High release-trust issue: source-built release still consumes upstream Go AAR

`settings.gradle.kts:28–33` fetches the Go core from `tjjh89017/stunmesh-go` GitHub release assets. `app/build.gradle.kts:25,140,153` makes **release** variants use that AAR even when a local AAR exists; there is no Gradle dependency-verification hash/lock for the asset. Thus compiling the forked Kotlin source is not enough to ship a self-audited binary. An upstream release asset/account change or compromised AAR remains in the phone trust chain. This is a supply-chain exposure, not evidence the current AAR is malicious.

There is also a conditional **repository-origin ambiguity**: `settings.gradle.kts` lists `google()` and `mavenCentral()` before the GitHub-release Ivy repository. The Ivy `content { includeGroup("dev.stunmesh") }` filter does not exclude that group from the earlier repositories. [Gradle states that repository-local includes are not exclusive and that repository order determines where a dependency resolves](https://docs.gradle.org/current/userguide/filtering_repository_content.html). If the same Go AAR coordinates were published to an earlier repository, a clean build could resolve that artifact instead of the expected GitHub asset. The exact Maven Central POM/AAR and Google Maven POM returned 404 at audit time ([android-go-aar-repository-order.txt](security-audit-evidence/android-go-aar-repository-order.txt)); this is a future risk, not evidence of substitution in the checked APK.

**Fix:** Build the Go AAR from a reviewed, pinned fork commit with pinned Go/gomobile/NDK/modules, store/verify its SHA-256, make the release build consume **that exact local artifact**, and fail if it is absent. If remote resolution remains, use Gradle `exclusiveContent` for the `dev.stunmesh` group and pin dependency checksums using [Gradle dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html). A scratch-only release variant using the independently rebuilt AAR passed `testDebugUnitTest assembleRelease`; no production Gradle file was modified.

### A-04 — Medium availability risk: a missing Go core can still show a running VPN

`app/src/main/java/dev/stunmesh/android/tunnel/TunnelManager.kt:34–44` falls back to `StubBackend` when the Go class is absent or construction fails. `StubBackend.kt:25–46` establishes a real Android TUN and reports `UP` but forwards **no packets**. If `stunmeshCoreVersion` is omitted or the Go binding fails in a custom release build, the interface can look connected while selected traffic blackholes. The official APK did contain Go native libraries; this is a custom-build/release failure mode, not a claim that the official release is currently stubbed. Even with the genuine Go backend, `mobile/node.go:116–118` emits `UP` **before** starting discovery and without checking for any peer handshake; `StatusScreen.kt:67–73` renders that as “Connected.” Thus the status indicates device setup, not verified tunnel reachability.

**Fix:** Prohibit the stub in release, fail the build without the exact AAR, and fail visibly at runtime if the core cannot load. Put a real handshake/packet health indicator on the status screen; `UP` alone means only device setup succeeded.

### A-05 — Medium: restored/corrupt encrypted config can be silently replaced

`ConfigRepository.kt:23–42` catches any read/decrypt/parse error and returns an empty `TunnelStore`. The next `save` (including a new active-tunnel selection) may replace a valid but temporarily unreadable config. Its write fallback deletes the existing file before trying a second rename; if that rename also fails, the old encrypted config is gone. `AndroidManifest.xml:9–12` allows backups, and the backup XML templates do not exclude `tunnel_config.bin`. A restored encrypted blob may lack its original Android Keystore key, then load as empty. [Android's EncryptedFile documentation explicitly warns that restoring an encrypted file can leave its key unavailable](https://developer.android.com/reference/androidx/security/crypto/EncryptedFile); this app uses its own AES-GCM file format but has the same device-bound-key concern. This is an availability/data-loss scenario, not a demonstrated decryption break. `ConfigRepository.kt:15–16` also claims the key never leaves secure hardware; the code does not request StrongBox or inspect `KeyInfo.getSecurityLevel()`, so the hardware claim is unsupported. Android documents that [Keystore hardware backing depends on the device and key](https://developer.android.com/privacy-and-security/keystore) and that [backup rules govern files restored on another device](https://developer.android.com/identity/data/autobackup).

**Fix:** Distinguish missing file from decrypt/parse failure; surface and preserve the latter, with no overwrite until the user explicitly resolves it. Use an atomic-file primitive that retains the previous good version across failed writes, and test a failed replacement. Exclude the encrypted blob from Auto Backup unless a working portable-key restore design is added. Query hardware security level if making a hardware-backed claim. Keep user-selected plaintext YAML exports clearly labeled as secrets.

### A-06 — Medium on manual log export: redaction misses generic plugin credentials

`TunnelConfig.kt:53–69` redacts WG private/PSK fields and plugin keys matching `token|secret|password|passphrase`, but does not match `api_key` and only redacts string values. `StatusScreen.kt:124–142` includes the redacted config in a manually exported log. `SecurityAuditTest.genericApiKeyIsNotRedactedFromLogExportConfig` demonstrates an `AUDIT-CANARY` credential surviving that export. Current built-in Cloudflare's `token` key *is* redacted; a generic/future imported plugin credential is the precondition. The app's full tunnel YAML export intentionally contains secrets and should not be confused with the log export.

**Fix:** Export an explicit allowlist of diagnostic fields or redact all plugin-config values by default, preserving only known non-secret keys. Test `api_key`, nested/list values and custom plugin fields.

### A-07 — Low/medium imported-profile limits and duplicate-key ambiguity

`MainActivity.kt:102–105` uses `InputStream.readBytes()` on a user-selected content URI before YAML or wg-quick parsing, with no size limit. An untrusted provider or selected oversized file can exhaust process memory. This requires the user's import action and does not grant network access. The exact published SnakeYAML 2.5 JAR's `Yaml(DumperOptions)` bytecode creates default `LoaderOptions` with `UnTrustedTagInspector`, a 50-collection-alias limit, a nesting limit of 50 and a 3,145,728-code-point document limit; duplicate keys remain allowed ([android-snakeyaml-loader-defaults.txt](security-audit-evidence/android-snakeyaml-loader-defaults.txt)). An audit-only JVM test confirmed that a second `wireguard.private_key` silently replaced the first in an imported YAML document ([android-duplicate-yaml-key.txt](security-audit-evidence/android-duplicate-yaml-key.txt)). The separate wg-quick `.conf` importer likewise lets a second `PrivateKey` silently replace the first ([android-wgquick-duplicate-key.txt](security-audit-evidence/android-wgquick-duplicate-key.txt)). Visual review of either duplicate-key profile can therefore be misleading. The app's JVM tests also rejected a synthetic arbitrary Java object tag and a 100-entry alias expansion; no YAML deserialization RCE was demonstrated. These parser limits apply **after** the unbounded file read and do not prove every YAML resource limit or remove duplicate-key ambiguity.

**Fix:** Bound reads to a small configuration limit, reject oversized/malformed inputs before persisting, disallow duplicate YAML keys and singleton wg-quick fields, and validate peer/plugin counts and string lengths.

### A-08 — Build and update-chain residual risks

The official `v0.2.1` APK SHA-256 is `9125271e7f205a3c222ada3704db86e9559fb359ca106c8305b4cece8aba97b3`. Android APK v3 signature verification passed; signer certificate SHA-256 is `6a732efac9b43afe280d513ca31b32c802537644b11333d5b34dd9d6179742cc`. I also downloaded and verified **all seven other published APK releases** (`v0.1.0-rc1` through `v0.2.0`): every local SHA-256 matched its GitHub release asset digest, APK signature verification passed, and all eight APKs used that **same signing certificate** ([android-all-releases-signing-continuity.json](security-audit-evidence/android-all-releases-signing-continuity.json)). Manifest `versionCode` increased 1 through 8 in release order ([android-all-releases-version-codes.txt](security-audit-evidence/android-all-releases-version-codes.txt)). This establishes signing-key continuity across the complete published APK release list as of 2026-09-13, but the self-asserted certificate and GitHub metadata do **not** independently establish publisher identity on first install or prove each release safe. The annotated `v0.2.1` source tag points at the audited commit but `git tag -v` reports no signature, so the tag alone does not authenticate its publisher ([android-release-tag-signature.txt](security-audit-evidence/android-release-tag-signature.txt)). There was no SourceStamp on `v0.2.1`. For your own Obtainium feed, use a stable self-controlled signing key, independently pin its certificate fingerprint, use monotonically increasing version codes, pin release commit/artifact hashes, and protect the release workflow; the fork's signing identity cannot upgrade an upstream-signed installed app in place.

The official APK and a source-built, unsigned `v0.2.1` APK using the **same upstream AAR** have identical entry names, manifest, both DEX files and 141/146 ZIP members. Four native library ZIP entries differ in packaging/non-runtime section metadata but have matching mapped segments when the ELF section-table pointer is normalized. This strongly supports Kotlin/manifest correspondence. The companion Go report also documents an **independent native rebuild**: after matching the upstream CI source/tool paths and `gomobile` temporary directory in an isolated audit build, the official and rebuilt ARM64/x86_64 ELF libraries differ only in build-ID notes; every other section, including executable code, is byte-identical. The 32-bit x86 executable section is byte-identical. ARMv7 has the same Go function layout and read-only data; every changed 32-bit `.text` word differs by the exact offset predicted by shifted `.text` and aligned target sections after an extra build-ID note (see [go-aar-armv7-layout-normalization.json](../stunmesh-go/security-audit-evidence/go-aar-armv7-layout-normalization.json)). That is strong correspondence, not formal semantic proof. The archive, generated Java JAR and complete 32-bit native libraries are still not bit-for-bit reproduced. This materially reduces release-only backdoor concern, strongest for 64-bit phones, without making the vulnerable source safe.

A tracked-file suffix inventory of the audited Android tree found one opaque executable/archive artifact, `gradle/wrapper/gradle-wrapper.jar` ([source-tree-opaque-payload-inventory.txt](../stunmesh-go/security-audit-evidence/source-tree-opaque-payload-inventory.txt)). The Gradle wrapper JAR matches the [official Gradle 9.0.0/9.1.0 wrapper hashes](https://gradle.org/release-checksums/) while the distribution URL/checksum pins Gradle 9.5.0. The declared 9.5.0 distribution checksum matches Gradle’s published value; an independent download matched that SHA-256 and all 683 archive payloads matched the isolated installed distribution ([distribution comparison](security-audit-evidence/gradle-distribution-installed-comparison.json)). Comparing `gradlew` and `gradlew.bat` to official 9.0.0 scripts found only the removed `-Dfile.encoding=UTF-8` default JVM option; their newer 9.5.0 counterparts differ more because the templates changed ([gradle-wrapper-official-checksums.json](security-audit-evidence/gradle-wrapper-official-checksums.json)). This is a stale-wrapper hygiene mismatch, not evidence of tampering; regenerate/verify the wrapper from the intended version. There is no dependency-verification metadata or lockfile. `settings.gradle.kts` also loads the [Gradle Foojay toolchain resolver](https://github.com/gradle/foojay-toolchains), which can resolve/download a JDK during a build; it is unnecessary if a reviewed JDK 21 is supplied explicitly. The exact resolved **runtime** Maven graph had 106 coordinates and no OSV-reported advisories as of 2026-09-13. All 73 cached content-bearing runtime AAR/JAR artifacts outside the separately audited Go AAR matched published SHA-256 metadata or independently downloaded bytes from Google Maven/Maven Central ([android-runtime-artifact-published-sha256.json](security-audit-evidence/android-runtime-artifact-published-sha256.json)). The **build-tool** graph had 115 coordinates; all 111 cached content-bearing build-tool JARs likewise matched their official repository bytes/checksums ([android-build-tool-artifact-published-sha256.json](security-audit-evidence/android-build-tool-artifact-published-sha256.json)). This checks consistency with the publishers at audit time, **not** whether a publisher or its upload account was compromised. Seven OSV/GHSA entries appeared across six build-tool components: `commons-lang3 3.16.0` (GHSA-j288-q9x7-2f5v), `jose4j 0.9.5` (GHSA-3677-xxcr-wjqv), `bcpkix-jdk18on 1.79` (GHSA-wg6q-6289-32hp), `bcprov-jdk18on 1.79` (GHSA-574f-3g2m-x479 and GHSA-c3fc-8qff-9hwx), `jdom2 2.0.6` (GHSA-2363-cqg2-863c), and `kotlin-gradle-plugin 2.2.10` (GHSA-r937-wjx7-w2jp). They are **not in the app runtime graph**, and the scan does not establish exploitability in this build. A repeat OSV query at 10:49 UTC returned the same resolved graphs and advisory IDs for all 218 unique coordinates ([rescan comparison](security-audit-evidence/android-osv-rescan-check.json)). The [per-advisory build-tool triage](security-audit-evidence/android-build-tool-advisory-triage.md) maps all seven flags to their specific triggers and resolved Gradle classpath paths. The [Kotlin advisory](https://github.com/advisories/GHSA-r937-wjx7-w2jp) broadly names build-cache deserialization, but its [fix commit](https://github.com/JetBrains/kotlin/commit/bf51df665b458fda7c3eaf436c4d88dc119d7ec6) identifies the affected code as **KAPT incremental caching**. This project applies no KAPT plugin, annotation processor or KAPT task, so that particular vulnerable path was not shown to run. Although the release job enables Gradle dependency caching and later reads signing keys, the `setup-java@v5` cache setting alone does not establish that hostile KAPT metadata is restored. GitHub says ordinary forked-PR caches are limited to their merge refs and cannot be restored by a release tag. No poisoned cache or reachable exploit was demonstrated. Keep KAPT absent, isolate signing from compilation/caches, and upgrade to a compatible patched plugin before adding KAPT.

The release job grants `contents: write` from its start and runs Gradle **after** decoding the signing keystore into `RUNNER_TEMP`. Its `actions/checkout@v7` step leaves `persist-credentials` at the [documented default `true`](https://github.com/actions/checkout/blob/main/README.md), so the job can run authenticated Git commands; v7 stores the credential in a separate runner-temporary file rather than directly in `.git/config`. A compromised build plugin or action running in that job could potentially read the keystore and the checkout credential even without the tag-injection flaw A-16. This is a trust-boundary consequence of the workflow, not proof of a compromised dependency. A safer fork release flow would build and test from verified dependencies in a read-only job, then sign a hashed artifact in a tightly scoped job with fresh caches, no compiler or unreviewed plugin execution, and only the publication permission needed at the final upload step.

Of the 106 resolved runtime Maven coordinates, 92 are `androidx.*`, 12 are `org.*` (JetBrains/Kotlin, `org.yaml:snakeyaml`, JSpecify), one is `com.google.guava:listenablefuture`, and one is the Go AAR coordinate. This is a **resolved graph, not 106 independent binaries shipped in the APK**: some entries are BOM constraints or metadata. The direct UI dependencies are AndroidX Activity/Compose/Material/Core/Lifecycle; SnakeYAML parses imported configuration; the Go AAR supplies tunneling. The official APK has two DEX files and two distinct native libraries across four ABIs: `libgojni.so` and AndroidX's `libandroidx.graphics.path.so`. No analytics, ad, crash-reporting or general HTTP client SDK was declared by the app. A bounded static scan of the official APK’s DEX and ARM64 libraries found only known app, dependency and documentation URL candidates, with no additional obvious telemetry destination ([android-apk-network-string-triage.md](security-audit-evidence/android-apk-network-string-triage.md)); this cannot detect dynamically constructed or hidden endpoints. AndroidX/Compose is the largest dependency family and a broader trust surface than a plain native UI; removing it would be a UI redesign, not a small audit hardening step. The Maven scan checks published advisories, not hidden malicious behavior, compromised build accounts or all transitive source code. The [direct dependency triage](security-audit-evidence/android-direct-dependency-triage.md) maps every declared runtime input to its resolved artifact and build-tool trust boundary.

The companion Go audit traced the Android core's package-import closure and found desktop-only `wgctrl`/netlink, YAML configuration and Wire-generated dependency injection entering through shared packages, alongside the essential embedded `wireguard-go` packet engine ([mobile-android-dependency-paths.json](../stunmesh-go/security-audit-evidence/mobile-android-dependency-paths.json)). It also compared **all 14 declared direct Go modules** to official source checkouts at their pinned commits/tags: all 3,230 delivered files, including WireGuard, Pion STUN, YAML and Go cryptography, matched byte-for-byte ([critical-go-source-module-comparison.json](../stunmesh-go/security-audit-evidence/critical-go-source-module-comparison.json)). A copied root LICENSE accounts for one file; 164 official Git files omitted from main module archives belong to nested modules. All 16 declared indirect Go modules also matched official snapshots, 2,961/2,961 delivered files; omitted Git files were nested-module trees ([indirect-go-source-module-comparison.json](../stunmesh-go/security-audit-evidence/indirect-go-source-module-comparison.json)). Together these comparisons cover every declared Go requirement and all 20 distinct external Go modules in the checked Linux/Android linked lists, but remain a source-provenance check rather than a full audit of those libraries, their authors, or Android Maven dependencies. A fork-specific mobile build can narrow that graph by separating shared endpoint types from desktop controllers and removing executable plugin constructors. Import presence alone does not show that all of the module's code survives Go linking.

The Android `lintDebug` and `lintRelease` tasks passed; release lint produced 22 findings about versions, unused resources and UI style, no security-specific issue. Lint does not inspect the Go core or establish source provenance.

The inherited CI and release workflows also use version tags rather than immutable action commits. This Android repository itself inherits the same privileged `.github/workflows/cla.yml` pattern as the Go repository: `pull_request_target`/`issue_comment`, `tjjh89017/stunmesh-cla@main`, write permissions, and an optional PAT secret. The [inspected CLA action at HEAD `6b6636b`](https://github.com/tjjh89017/stunmesh-cla/blob/6b6636bb073860f857f59a3efee6d08d17fe8c33/action.yml) delegates to `contributor-assistant/github-action@v2.6.1` with the workflow token and optional PAT; the wrapper showed no custom executable code, but adds another privileged dependency. GitHub Actions were disabled on both new `Owner` audit forks on 2026-09-13, and the API readback confirmed this. Remove the unneeded CLA workflow from the personal fork, or tightly pin/review it before re-enabling Actions, and protect any signed-release keys.

An additional [zizmor](https://docs.zizmor.sh/usage/) v1.30.1 offline auditor scan produced 36 raw workflow warnings ([zizmor-ci-triage.json](security-audit-evidence/zizmor-ci-triage.json)). Three high-confidence release-tag template warnings corroborate the independently reproduced A-16 path. Two high-confidence flags in the CI workflow occur only in a `ref_type=tag` branch, while that workflow triggers on branch pushes and pull requests, so those two are not reachable as tag-triggered commands in this workflow. Six warnings concern unpinned actions; a low-confidence cache-poisoning warning is a lead, not evidence of a poisoned cache. The tool performs static, offline analysis of workflow definitions, not actual GitHub runner execution.

### A-09 — External DNS fallback is an explicit trust/metadata choice

`mobile/node.go:22` falls back to Google/Cloudflare public DNS addresses when Android has not supplied underlay resolvers. `StunmeshVpnService.kt:161–216` tries to feed underlay DNS via network callbacks, but there is an initial window and failure path. This is not a backdoor; it is a public DNS dependency and possible hostname metadata disclosure. For a private deployment, require known underlay DNS or document the fallback and prefer literal STUN/proxy addresses where operationally viable. HTTPS still protects DHT content in transit; DNS reveals queried hostnames.

### A-10 — Medium availability: Android's default refresh equals OpenDHT's expiry

`mobile/config.go:112–114` defaults to 600 seconds, while OpenDHT's [default stored-value expiration is ten minutes](https://github.com/savoirfairelinux/opendht/blob/be210e27da674be618e2d4cbc422a897b3daff96/include/opendht/value.h). One delayed or failed publish can leave the phone's record absent before the next cycle. `StunmeshVpnService.onDefaultNetworkChanged` renews the TUN fd but does not ask the Go controller to run discovery/publish immediately; `controller.run` waits for its next ticker tick. After a Wi-Fi/cellular handover, a newly changed public UDP mapping therefore may not be advertised for up to the refresh interval. The exact connection behavior depends on Android socket/network handling and was not device-tested. Set a much shorter cadence (for example, one minute), trigger a discovery cycle on underlay change, leave OpenDHT dedup disabled, and verify reconnect after deliberately failed refresh cycles and handovers. This does not affect WG cryptographic authentication.

### A-11 — Medium for debug APKs: an exported receiver imports tunnel configuration from any app

`app/src/debug/AndroidManifest.xml:12–14` exports `ConfigImportReceiver` without a permission. The merged **debug** manifest contains it; the merged **release** manifest and official release APK do not ([android-manifest-exposure.json](security-audit-evidence/android-manifest-exposure.json)). `ConfigImportReceiver.kt:17–32` accepts base64 JSON from a broadcast, replaces a same-named tunnel and sets it active in the encrypted repository. Per [Android's receiver guidance](https://developer.android.com/privacy-and-security/risks/insecure-broadcast-receiver), an unprotected exported receiver can be invoked by other installed apps. A malicious local app could therefore change the configuration of an installed debug APK without the VPN user's import action; the changed tunnel may be used on a later start/restart. This is a source/merged-manifest finding, **not** a device exploit test, and it does not apply to the current release APK. The receiver does not itself read out existing secrets or start the VPN.

**Fix:** Do not use debug APKs with real tunnel credentials. Remove this broadcast hook or restrict it to a signature-protected test build and verify that no release variant exports it. Keep test injection behind explicit developer/test tooling, with a bound on the input size.

### A-12 — Conditional network reachability: a DHT proxy can redirect phone requests

The Go core's OpenDHT HTTP client follows redirects by default. The companion Go audit test proved that a configured synthetic **HTTPS** proxy could redirect its request to an unrelated local **HTTP** URL. On Android, these discovery sockets are protected out of the VPN, so a compromised configured proxy could cause requests to LAN destinations reachable from the phone's underlay. The test ran in an isolated Linux namespace, **not** on a phone or home router; no secret extraction or WG authentication bypass was demonstrated. Disable DHT redirects or restrict them to same-origin HTTPS in the Go core, and use an HTTPS proxy endpoint. Android documents that its [cleartext-traffic flag is best-effort for socket-level clients](https://developer.android.com/guide/topics/manifest/application-element), so it is not a sufficient fix by itself.

### A-13 — Medium user-action risk: full tunnel export has no in-app secret warning

`MainActivity.kt:81–90` writes `TunnelYaml.encode(tunnel)` to the user-selected document provider, including the WG private key, optional PSK and plugin API token. `TunnelListScreen.kt:150–152` exposes the action as an icon-only Export control, with no in-app warning that the destination receives plaintext credentials. The user must choose Export and a destination; this is **not** automatic exfiltration or a hidden backdoor. Show a clear warning before export, distinguish encrypted backup from plaintext configuration transfer, and label the file/output as sensitive.

### A-14 — Medium on manual log export: malformed imports can copy secret text into logs

`MainActivity.kt:96–121` appends a failed import's full exception message to the rolling log, which `StatusScreen.kt:124–142` includes verbatim in a user-selected log export. `TunnelYaml.decode` embeds SnakeYAML's parser message, and `WgQuickConf.decode` includes the full malformed line when `=` is absent. Two synthetic JVM audit tests show a credential-like canary from an invalid `private_key`/`PrivateKey` line appearing in those messages. Thus the A-06 config redaction does not ensure the whole log export is free of secrets. This requires a malformed user-selected import followed by manual log export; no automatic network exfiltration was shown.

**Fix:** Log a bounded error category and line number, without source lines, parser snippets, or raw exception messages. Treat the entire rolling log as sensitive until it is generated exclusively from allowlisted fields; test malformed private-key and plugin-token inputs.

### A-15 — High availability: VPN service never enters the foreground

`StunmeshVpnService.kt` starts the tunnel from `onStartCommand` but never calls `startForeground`; the manifest declares neither `FOREGROUND_SERVICE` nor a foreground-service type. The app targets API 36 and supports API 28+. [Android's VpnService documentation](https://developer.android.com/reference/android/net/VpnService) says that on Android 8.0+ the system gives a background-started VPN a short temporary allowlist and **will shut down the app unless it promotes the service to the foreground**. This is especially relevant when Android restarts an always-on VPN after reboot or process death. I did not run an Android device to measure when shutdown occurs, but the required call and manifest declarations are absent from the reviewed source and merged release manifest.

**Fix:** Add a persistent VPN status notification, foreground promotion during startup, and orderly demotion on stop. For target API 36, declare the appropriate foreground-service permissions and type; [Android documents `systemExempted` for VPN apps configured in system VPN settings](https://developer.android.com/develop/background-work/services/fgs/service-types). Verify actual eligibility and startup on the intended phone, including user-started, always-on reboot, app upgrade and network handover paths. If always-on is unsupported, explicitly opt out in the manifest instead of advertising it by default.

### A-16 — High release-key exposure risk: tag name executes as shell code in signing workflow

**Demonstrated locally without a GitHub run.** `.github/workflows/release.yml:31,69,79` interpolates `${{ github.ref_name }}` directly into `run:` shell scripts on a pushed `v*` tag. The synthetic tag `v$(printf${IFS}AUDIT_CANARY)` passes `git check-ref-format` and, when substituted into the actual line 31 command, causes Bash command substitution even though the value appears inside double quotes. The local result was `VERSION_NAME=vAUDIT_CANARY` ([android-release-tag-injection.json](security-audit-evidence/android-release-tag-injection.json)). [GitHub documents that context expressions are expanded into the temporary shell script before execution and that ref names are untrusted input](https://docs.github.com/en/actions/concepts/security/script-injections). No tag was pushed to GitHub, so this does not establish that GitHub accepts this specific name or that a remote secret was read. The precondition is control over a tag that triggers the release workflow; tag protection may restrict that control. The release job also decodes its signing keystore into `RUNNER_TEMP` and later runs a step with a write-capable `GITHUB_TOKEN`, so an injected command in that job could read the keystore or alter published artifacts. This is an independently important release-pipeline flaw even if the checked source APK is benign.

**Fix:** Treat the tag as data by passing it through a step `env:` variable and referencing the variable with a quoted shell expansion; validate it against a narrow release-tag pattern before use. Protect release tags, keep signing keys outside untrusted build contexts, and pin/review actions and the CLA workflow before enabling Actions on the fork. A local source build remains safe from this specific GitHub runner path.

### A-17 — Medium, conditional: an all-zero imported peer key enables public discovery forgery

The Android `TunnelYaml.decode`/`TunnelConfig.fromJson` path and the Go mobile parser accept a correctly sized but low-order all-zero WireGuard peer public key. `SecurityAuditTest.importedYamlPreservesLowOrderPeerPublicKeyAcrossGoBoundary` confirms the Kotlin import/JSON path. The Go core's NaCl `box` derives the same publicly computable cipher key regardless of private scalar for that point. The companion Go audit tests prove that such a record can be decrypted by an unrelated key and that an arbitrary synthetic DHT writer can then use A-01 to enroll a new WireGuard peer without either configured private key or PSK ([go-low-order-key-composition.txt](../stunmesh-go/security-audit-evidence/go-low-order-key-composition.txt)). This requires a **malformed configured peer key** and knowledge of the local public key/DHT slot; it does not apply to correctly generated peer keys. The malformed peer cannot complete a WG handshake, but the injected new peer can be valid. The composition was tested in the Linux build of the same Go mobile core, not on Android OS or a public DHT.

**Fix:** Reject all-zero and other low-order public keys during import/edit, in Go mobile parsing and before discovery publication. The Go core must also fix A-01 so discovery never changes peer authorization, even for a properly generated key.

### A-18 — Medium availability: editing after connection can clear the active tunnel

**Confirmed from source; not device-tested.** `MainActivity.kt:57` loads a `TunnelStore` once into Compose state. Connecting calls `TunnelManager.start` (`TunnelManager.kt:84–88`), which writes a new `activeId` through a separate `ConfigRepository` but never updates that in-memory UI store. If the UI store had no active tunnel or a different one, a later edit/save, import or delete writes its stale `activeId` back to disk (`MainActivity.kt:114–115,171–174,196–198`). A running tunnel may continue until restart, but `StunmeshVpnService.up` then reads no or the wrong active tunnel (`StunmeshVpnService.kt:69–81`). This can break always-on recovery after an otherwise ordinary edit. The condition depends on the active selection changing while the activity remains alive; it is not a remote authentication bypass.

**Fix:** Make the repository the single state source, update the UI state after every active-tunnel change, and perform read-modify-write operations atomically against the latest store. Add a test that connects tunnel B, edits or imports, then restarts the service and checks that B remains active.

### A-19 — Medium conditional: editing a multi-plugin tunnel redirects peers to one store

**Confirmed from source; not device-tested.** YAML import supports multiple plugin instances and distinct per-peer `plugin` references (`TunnelYaml.kt:112–130`); `SecurityAuditTest.importedTunnelCanKeepDistinctStoresForDifferentPeers` confirms such a synthetic import passes. But `TunnelEditorScreen.kt:77–86` displays only the first plugin, and Save recreates a **single** plugin while assigning its instance to **every** peer (`TunnelEditorScreen.kt:210–218,247–253`). An ordinary name or key edit to an imported multi-store tunnel therefore silently sends every peer's encrypted endpoint record to the first provider and stops using the other stores. The newly selected provider sees each affected peer's source IP, record index and timing; peers expecting their original store may fail to reconnect. This requires a multi-plugin imported config and a later editor save, not a remote attack or plaintext disclosure by itself. Save also omits `logLevel`, resetting that setting to its default.

**Fix:** Preserve the full plugin list and each peer's store reference during unrelated edits. If the UI supports only one store, block editing multi-store configs with an explicit explanation instead of silently rewriting them. Test that importing two stores, editing the tunnel name and reloading leaves both mappings intact.

### A-20 — Medium conditional availability: underlay handover can miss TUN renewal

**Source and platform-contract finding; not device-tested.** `StunmeshVpnService.kt:117–129` registers `registerDefaultNetworkCallback` and renews the TUN only when its reported `Network` object changes after the first event. [Android defines this callback as the application's default network, which may be the VPN itself](https://developer.android.com/reference/android/net/ConnectivityManager). Its separate DNS callback deliberately requests `NET_CAPABILITY_NOT_VPN` (`StunmeshVpnService.kt:162–170`), and the source comments explicitly acknowledge that the default callback can report the VPN once it is up. If the VPN remains the app's default while Wi-Fi changes to cellular underneath it, a physical underlay change does not necessarily change the default callback's `Network` object, so `onDefaultNetworkChanged` may never call `renewTun`. The protected outer sockets may still recover by route changes or periodic discovery, so this is a conditional handover risk, **not** proof that every handover fails.

**Fix:** Observe non-VPN network availability/loss/capability changes and the actual underlay used by protected sockets, then trigger the needed socket/TUN and discovery refresh on a real underlay change. Use the existing non-VPN callback as the starting point, and test Wi-Fi↔cellular handover on the target phone with the VPN active and always-on. Avoid treating a replacement VPN `Network` as evidence that the physical underlay changed.

### A-21 — Medium conditional confidentiality: rejected DNS settings fall back silently

**Source and Android API finding; not device-tested.** `StunmeshVpnService.kt:107–111` catches an error from `Builder.addDnsServer(dns)`, logs a warning and continues establishing the VPN. If every explicitly configured DNS address is invalid or rejected, the builder has no DNS server. [Android's `VpnService.Builder` documentation says it then uses the default network's DNS servers](https://developer.android.com/reference/android/net/VpnService.Builder), which may be outside the intended WireGuard path. The UI can still say “Connected” because that state does not check DNS or a peer handshake (A-04). This requires a malformed/rejected DNS setting and a system fallback that actually uses an underlay resolver; it is not evidence of a leak in a valid configuration or of a live device leak.

**Fix:** Validate all configured DNS addresses before creating the VPN, and fail tunnel startup visibly if an explicitly requested server cannot be installed. If the user intentionally leaves DNS empty, make that fallback choice clear. On the target phone, verify resolver selection and query routing with valid and invalid DNS entries, including always-on/lockdown mode.

### A-22 — Medium on manual log export: proxy URL passwords survive redaction

**Demonstrated in a synthetic JVM regression test.** `TunnelConfig.redactSecrets()` only redacts string values whose **key** matches `token|secret|password|passphrase`. Both an OpenDHT `endpoint` string and an `endpoints` list can therefore retain `https://user:password@host` userinfo. `opendhtUrlUserinfoSurvivesRedactedLogConfig` passed for both forms after `TunnelYaml.encode` ([android-opendht-url-userinfo-export.txt](security-audit-evidence/android-opendht-url-userinfo-export.txt)). `StatusScreen.buildLogExport` labels that YAML “secrets redacted” and appends rolling log lines unchanged. The companion Go test shows a failed proxy request also returns the password-bearing URL in an error; `mobile/controller.go` forwards it to `TunnelManager.onLog`. A-06 covers generic plugin keys separately. This is conditional on a credential-bearing proxy URL and a user who views or shares the log export; no automatic remote upload was found.

**Fix:** Reject URL userinfo or redact it in every endpoint field, including list values; sanitize errors before they enter the rolling log, and make log export strip any residual URL credentials. Verify the output with canary credentials for both success and failure paths.

### A-23 — Medium conditional privacy: masked secret fields request an ordinary text keyboard

`TunnelEditorScreen.kt:103,114,173` sends the WireGuard private key, peer PSK and optional Cloudflare API token through a shared `FormField`. That field sets `PasswordVisualTransformation` but does not set `keyboardOptions` (`TunnelEditorScreen.kt:274–290`). The exact resolved Compose Material3 1.4.0 implementation passes default keyboard options independently of the visual mask; Compose Foundation 1.10.4 resolves those defaults to a normal text keyboard with autocorrect enabled. The mask does mark password semantics for accessibility, but it does **not** request Android's password input type from the IME ([exact-version source trace](security-audit-evidence/android-secret-ime-mode.txt)). [Android documents `KeyboardType.Password`](https://developer.android.com/reference/kotlin/androidx/compose/ui/text/input/KeyboardType) as the option that disables suggestions and learning in cooperating keyboards. A third-party keyboard may therefore suggest or retain manually entered keys/tokens as normal text. I did not test an Android keyboard or demonstrate credential upload; an IME can see keystrokes regardless of input hints and is a separate trust dependency.

**Fix:** Supply `KeyboardOptions(keyboardType = KeyboardType.Password, autoCorrectEnabled = false)` for all secret fields, or use Compose's secure text field API after verifying compatibility. Keep the visual mask and test the actual `EditorInfo.inputType` on the intended Android version. Avoid manually typing long-lived WireGuard keys on an untrusted keyboard.

## Verification and limits

Eight downloaded Go, Temurin and Google Android SDK/NDK/build-tool/platform archives matched publisher-served checksum metadata ([toolchain checksum evidence](../stunmesh-go/security-audit-evidence/build-toolchain-publisher-checksums.json)). Every regular file and symlink in the installed NDK 29, build-tools 36/36.1 and platform 36.1 matched the corresponding official ZIP: 9,655 NDK regular files and 37 symlinks, 336 build-tool regular files, and 11,373 platform regular files ([installed-file comparison](security-audit-evidence/sdk-installed-archive-comparison.json)). Google's SDK metadata uses SHA-1 for these ZIPs. This checks distribution consistency, not the source or safety of those toolchains; generated SDK metadata was not compared to archive content.

With the Google Android SDK installed **only in the isolated audit workspace as authorized**, an offline run of `testDebugUnitTest assembleRelease lintDebug lintRelease` passed ([android-full-offline-verification.txt](security-audit-evidence/android-full-offline-verification.txt)). After adding the audit-only import and redaction regressions, the latest isolated offline JVM suite passed **28 tests, zero failures** across five suites: 13 audit tests and 15 baseline tests ([android-full-jvm-suite-results.json](security-audit-evidence/android-full-jvm-suite-results.json), [android-full-jvm-gradle-log.txt](security-audit-evidence/android-full-jvm-gradle-log.txt), [android-audit-test-results.xml](security-audit-evidence/android-audit-test-results.xml)). Individual synthetic reproductions are linked beside their findings. The Go mobile core passed race-enabled tests and the synthetic end-to-end attack test. The official APK was signature/manifest/DEX-compared to a version-matched build; exact runtime/build-tool dependency coordinates were queried against OSV. A locally rebuilt Go AAR was produced and a scratch-only release build using that AAR passed.

A redacted history pattern scan inspected 149 blobs across 55 commits for common PEM private keys, AWS/GitHub/Stripe/Slack token formats and HTTP URL userinfo, finding zero matches ([android-secret-pattern-scan.json](security-audit-evidence/android-secret-pattern-scan.json)). It does not detect every secret shape or malicious change.

No Android emulator or device with KVM was available, so VPN lifecycle, Binder/Keystore behavior, network handover and actual cellular NAT traversal were **not** run on Android. The Google SDK, Gradle, AndroidX, Go runtime and all transitive source code were not independently audited. No compromised dependency or real-world exploitation was established, and no tool can prove absence of backdoors from a finite review.

**Release gate:** fix A-01 in the Go core and reject A-17 low-order keys; enforce built-in-only plugins; make release use a verified fork-built AAR and never silently stub; fix A-16 before enabling signed release workflows; implement the foreground VPN lifecycle; protect encrypted config against silent loss/backup restore, stale active selection and multi-store editing; fix log redaction, secret keyboard mode and import bounds; set a safe OpenDHT refresh cadence; review build-tool advisories; then install a self-signed fork APK on a test Android phone and verify handshake, traffic, disconnect, reboot, always-on restart, handover and update behavior before allowing access to the home network.
